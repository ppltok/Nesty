TL;DR

Growth is up sharply, quality of completion is the problem. Signups nearly doubled week-over-week (23 → 42), but onboarding completion slipped from 91.3% to 83.3%, and ~29% of "completed" users have an empty registry (10 of 35, 0 items). Co-parent invites are going out fine (5 sent this week) - the bottleneck is acceptance (1 of 5). Separately, Microsoft Clarity captured almost no production sessions this window (only internal/dev traffic), so page-level friction data is effectively dark - that itself is finding #1.

Findings & Recommended Fixes

1. Clarity is not capturing production traffic High

What's wrong: The Clarity live-insights API returned only 5 total sessions over 3 days - all MacOSX / PC / Israel, landing on localhost:5173 and Electron, i.e. the developer's own machine. Zero real production visitor sessions, despite ~18 signups in the same 3-day span. Every friction metric (RageClick, DeadClick, QuickBack, ScriptError, ErrorClick) reads 0 - not because the site is clean, but because there is nothing to measure.

Evidence: Traffic = 5 sessions / 3 distinct users / 1 bot; PopularPages are all localhost:5173/* + https://Electron; OS 100% MacOSX; Country 100% Israel. The Clarity tag itself is correctly installed and ungated in nesty-web/index.html (project xi1xr7lx6t, no consent wall), so the tag isn't the bug.

Most likely cause: Nearly all real signups arrive from Instagram/Facebook ads, which open in Meta in-app webviews on mobile where Clarity frequently fails to establish a recording session (in-app browser + storage partitioning). Result: the one audience we most need to watch (paid-social mobile) is invisible.

Suggested fix:

  • Open the Clarity dashboard → Recordings, filter last 3 days, and confirm the live count. If it's near-zero, this is real.
  • Verify the tag fires inside a Meta in-app browser: open a Nesty ad link from the Instagram app on a phone and check whether the session appears in Clarity within a few minutes.
  • If in-app webviews are the gap, add a lightweight first-party event fallback (we already have GTM + tracking.ts) so onboarding step drop-off is measurable even when Clarity can't record - don't let the weekly UX signal depend solely on Clarity.
  • Until fixed, treat the "0 friction signals" in these reports as no data, not no problems.

2. Completed-but-empty: ~29% finish onboarding with an empty registry High

What's wrong: 11 of 35 completed users have 0 items - but 1 of those (gilibergman) is actually a co-parent on someone else's registry (they signed up by accepting Ron's invite), so the true empty-owner count is 10 of 35 (~29%). In the flow, step 7 (first_item) is skippable and handleComplete() marks onboarding_completed=true regardless of whether anything was added (Onboarding.tsx, handleSkip at step 7 → complete). A registry with nothing in it can't be shared and gets no gifts - this is a silent activation dead-end.

Evidence: 34 of 35 completers created a registry, but only 24 added ≥1 item; avg 2.6 items among all completers. Note several empty-completers have past due dates (e.g. 2026-03-07, 2026-05-18, 2026-06-04) - already-postpartum users for whom a registry-first flow may simply be the wrong fit.

Suggested fix:

  • Seed the registry on skip. Pre-select 1–2 popular curated items on the first-item step so that even a "skip" leaves the registry non-empty (the curated picker already exists via handlePickItem). Turns an empty exit into a warm start the user can edit.
  • Make the dashboard empty-state do the pushing. For completers with 0 items, the dashboard should open on a focused "add your first item" state (paste-URL + curated grid), not a generic dashboard. Reuse the existing checklist_nudge / engagement-email infra to follow up at 24–48h.
  • Add a postpartum branch. When due_date is in the past, the first-item copy should pivot from "build your registry" to a postpartum-relevant ask - otherwise these users correctly bounce off a pregnancy-registry framing.

3. Onboarding completion fell 8pp - coincides with the new WhatsApp phone step Medium

What's wrong: Completion dropped 91.3% → 83.3% (7 abandoners this week). A new whatsapp_phone step (step 5) was added to the flow in the last release (1cf3c5d Onboarding: WhatsApp phone-capture step). Adding a personal-data ask mid-funnel is a classic drop point.

Evidence: All 7 abandoners this week have null due_date, null UTM, null landing_page - i.e. their profiles are essentially empty, consistent with dropping at the very first screen (step 1 name, before due-date is captured). So the aggregate decline could be first-screen friction rather than the phone step specifically - we can't tell the exact step from the DB because the last-step-reached lives only in the Clarity onboarding_step tag (see finding #1). The correlation with the new step is a hypothesis to confirm from recordings.

Suggested fix:

  • Confirm the exact abandonment step from Clarity recordings (filter tag onboarding = in_progress). If drop clusters at step 5, soften or defer the WhatsApp ask to after completion.
  • The WhatsApp step is already skippable - make the skip more visible and reassure why the number is asked (delivery / co-parent), per the "no pressure" brand rule.
  • If drop clusters at step 1, the issue is the entry screen, not the phone step - investigate load/first-paint on mobile in-app browsers.

4. Co-parent: invites are sent, but few get accepted Medium

Correction from an earlier draft: co-parent invites are not zero. The initial measure counted registries.partner_id, which is only set once a co-parent accepts and links - so it silently dropped every sent-but-pending invite. Reading the real source (registry_invitations) flips the picture: the step works, the acceptance is the leak.

What's actually happening: 5 invites sent this week by 5 distinct inviters (4 last week), but only 1 accepted (1 last week). The 4 unaccepted are all pending from this-week signups. All-time, only 16 of 422 registries (3.8%) end up with a linked partner - consistent with a sending rate that's fine and an acceptance rate near 20%.
